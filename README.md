# wikipedia-trends

Agent Skill (see `SKILL.md`) for analyzing Wikipedia pageview trends. This file is for the human maintaining the repo — the agent reads `SKILL.md` instead.

## Setup

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

## Directory purposes

| directory | what's in it | persists? |
|---|---|---|
| `scripts/` | the skill's actual code | yes — source, keep |
| `references/` | API/threshold/limitations documentation for the agent | yes — source, keep |
| `cache/` | automatic API response cache, keyed by request params | yes, but **never expires on its own** |
| `data/` | archived intermediate JSON (pageviews + analysis) from past runs | yes, but grows unbounded |
| `reports/` | generated PDF reports + chart PNGs | yes, but grows unbounded |

`cache/`, `data/`, and `reports/` are all runtime output, not skill source — they're gitignored. None of the three are cleaned up automatically:

- `cache/` can go stale (the agent is instructed to check `cache_age_days` and ask before trusting old cached data, but the file itself is never deleted).
- `data/` and `reports/` accumulate one set of files per analysis/report ever run — nothing removes old ones.

**Periodically clean these out by hand** (`rm -rf cache data reports`, or prune selectively) if the directory is getting cluttered or you want to force fully fresh data. Safe to delete anytime — everything in them is reproducible by re-running the pipeline.

## Як це працює (логіка пайплайну)

Нижче — пояснення ключових рішень, чому вони саме такі, і які компроміси за ними стоять.

### 1. Тема → поняття → назва статті в кожній мові (`resolve_topic.py`)

Wikimedia Pageviews API приймає лише **точну назву статті**, а користувач формулює **тему** довільною мовою ("інтервальне голодування", "штучний інтелект"). Тому пряме "вгадування" назви статті ненадійне: назви різняться між мовами, а той самий рядок може означати геть різні речі різними мовами.

Замість пошуку в кожній мовній Wikipedia окремо, ми йдемо через **Wikidata**: там кожне поняття має єдиний мовно-незалежний ідентифікатор (QID), а сам QID містить список `sitelinks` — точних назв статей у кожній мовній версії Wikipedia, які всі стосуються **того самого** поняття. Це дає дві переваги:
- один запит одразу дає назви для всіх потрібних мов, замість N окремих пошуків;
- гарантія, що це справді одне й те саме поняття в різних мовах, а не випадковий текстовий збіг.

**Неоднозначність** (омоніми, кілька сутностей з однаковою назвою) вирішується не вгадуванням, а явним порівнянням, наскільки кожен кандидат "широко покритий" мовами Wikipedia (кількість `sitelinks`) — якщо жоден кандидат не домінує явно, скрипт повертає статус `ambiguous` і список кандидатів, а не мовчки обирає перший-ліпший.

**Якщо статті немає в якійсь мові** — це чесно позначається (`missing_languages`), і ця мова просто виключається з порівняння. Раніше був експериментальний фолбек (перекласти тему й пошукати суміжне поняття в цій мові), але його прибрали: заміна часто виявлялась іншою темою по суті, а не тим самим поняттям іншою мовою — див. розділ "Плани на майбутнє" нижче.

### 2. Отримання статистики переглядів (`fetch_pageviews.py`)

Дані беруться з офіційного **Wikimedia Pageviews API** (REST) за точною назвою статті, мовою і періодом.

**Важливий фільтр:** ми запитуємо `agent=user` — це означає **лише живий, людський трафік**, без ботів і краулерів. Без цього фільтра "інтерес до теми" був би спотворений автоматичними скрейперами, які не мають нічого спільного з реальною зацікавленістю аудиторії.

**Також важливо:** ми запитуємо `access=all-access` — тобто перегляди **з усіх типів пристроїв разом** (десктоп, мобільний сайт, мобільний застосунок), без розбивки. API технічно дозволяє запитувати кожен тип окремо, але зараз ми цим не користуємось.

**Можливе покращення на майбутнє:** будувати окремі графіки по типах пристроїв/доступу (desktop vs mobile-web vs mobile-app), а не тільки сумарний трафік. Це б показало, наприклад, чи тема більше "мобільна" (масовіша, повсякденна) чи "десктопна" (частіше дослідницька/професійна аудиторія) — корисний додатковий сигнал для рішень про продукт. (Є суміжний скрипт `device_profile.py`, який уже вміє показувати desktop/mobile розподіл, але лише **для всього мовного розділу в цілому**, не для конкретної теми — Wikimedia Pageviews API просто не має такого зрізу "перегляди статті X по пристроях", лише сумарно, тому це вже окрема, менш точна метрика.)

### 3. Чому ми кешуємо дані (обмеження швидкості запитів)

І Wikidata, і Wikimedia Pageviews API мають доволі жорсткий **rate limit** для анонімних запитів — за короткий сплеск запитів сервер починає відповідати помилкою 429 ("забагато запитів") і потребує кількох секунд на відновлення.

Тому кожен запит до API **кешується на диск** за ключем (мова, стаття, період, гранулярність тощо). Повторний або суміжний запит (наприклад, "додай ще одну мову до порівняння") бере вже наявні дані з диска замість повторного звернення до API — це і швидше для користувача, і не перевантажує зовнішній сервіс.

**Важливий нюанс:** кеш **не має терміну придатності** — сам файл ніколи не видаляється автоматично. Замість цього кожен запит повертає `cache_age_days` (скільки днів тому дані закешовано), і якщо це давно — користувачу прямо повідомляється про це з вибором: використати старі дані чи дотягнути свіжі (`--no-cache`). Тобто "свіжість" — це прозорий вибір користувача, а не прихована проблема.

### 4. Ми оцінюємо не тільки трафік на тему, а й трафік усієї Wikipedia-мови (`analyze_trends.py`, baseline)

Ріст чи спад переглядів конкретної статті сам по собі може вводити в оману: якщо **весь** мовний розділ Wikipedia за цей час теж почав отримувати більше чи менше відвідувачів (наприклад, через сезонність, через ріст популярності Wikipedia в цій мові загалом, чи навпаки — через відтік читачів до AI-чатботів замість пошуку), то зміна трафіку однієї статті частково (чи повністю) пояснюється цим загальним ефектом, а не специфічним інтересом саме до теми.

Тому для кожного аналізу ми **автоматично** тягнемо ще один показник — сумарний трафік усього мовного розділу Wikipedia (`aggregate`) за той самий період, і порівнюємо: **зростає/спадає стаття швидше, повільніше чи так само, як весь розділ загалом?**
- Якщо зміна статті близька до зміни всього розділу — це, ймовірно, просто загальний тренд трафіку платформи, а не специфічний інтерес до теми.
- Якщо стаття зростає/спадає **помітно швидше** за загальний тренд — це вже специфічний сигнал саме про тему.

Це дає набагато чесніший висновок, ніж голе число "перегляди зросли на 20%" — таке число без контексту нічого не каже про те, чи це реальний інтерес до теми, чи просто "весь інтернет зараз більше читає Wikipedia".

### 5. Чому ми ігноруємо деякі сплески і неповні місяці (`analyze_trends.py`)

Сирі дані переглядів часто містять шум, який спотворює справжній тренд, якщо рахувати його наївно:

**Неповні періоди.** Якщо запитати діапазон, що закінчується сьогоднішньою датою (наприклад, "поточний місяць"), Wikimedia поверне дані лише за ту частину місяця, яка вже минула — цей "місяць" виглядатиме штучно заниженим (чи, навпаки, штучно високим, якщо рахувати накопичувальну суму), просто тому що він неповний, а не тому що інтерес справді змінився. Ми **відкидаємо такі неповні періоди** з розрахунку — причому звіряємо не лише запитану дату, а й **реальну поточну дату** (бо можна випадково запросити діапазон "до кінця місяця", хоча місяць ще не завершився).

**Аномальні сплески/провали (викиди).** Одна конкретна новина, вірусний момент чи спад через технічний збій можуть дати одноразовий стрибок чи провал у даних, який не є частиною стійкого тренду. Ми визначаємо такі точки статистично — через медіану і **MAD** (median absolute deviation, стійкіший за звичайне середнє й стандартне відхилення метод, бо сам викид менше спотворює саму оцінку "норми") — і **виключаємо їх із розрахунку тренду й відсотка зміни**, хоча вони й лишаються видимими на сирому графіку.

**Чому це обґрунтовано, а не "підгонка під потрібну відповідь":** мета — відповісти на питання "чи є стійка зміна інтересу до теми", а не "що сталось в один конкретний день". Одна вірусна новина не означає стійкий тренд; аналогічно, неповний місяць — це артефакт вимірювання, а не сигнал. Обидва типи винятків **явно позначаються** у звіті (дати викидів, дати відкинутих періодів) — нічого не приховується, лише не змішується з оцінкою тренду.

**Відома межа цього підходу:** глобальний статистичний тест (медіана/MAD по всьому ряду) не завжди ідеально відрізняє "аномалію" від "природного краю сильного тренду" (наприклад, на ряді з різким спадом перші, найвищі точки іноді помилково позначаються як "викиди"), і не завжди ловить **регулярну сезонність** (наприклад, щорічний сплеск інтересу до теми у вересні через початок навчального року) — оскільки такий сплеск може бути недостатньо екстремальним відносно *всього* ряду, щоб його визначити статистично. Ба більше: якщо викидів декілька і вони йдуть підряд чи близько одне до одного — це вже може бути не шум, а реальна, варта окремої уваги подія (перевірено на практиці: тема з двома потужними сплесками за кілька місяців — це радше сигнал про щось реальне, ніж випадковість).

### Метрики: що саме означає кожне число у звіті

| Метрика | Що означає |
|---|---|
| `growth_pct` | Зміна переглядів за весь період у відсотках. Рахується не як "перший день проти останнього" (це надто вразливо до одного випадкового провалу/сплеску на самому краю), а як різниця між **середнім за першу чверть** періоду і **середнім за останню чверть**. |
| `relative_growth_pct` | Те саме, але **відносно зміни всього мовного розділу Wikipedia** за той самий час (див. розділ 4 вище). Велике додатне значення — специфічний ріст інтересу до теми; велике від'ємне — тема втрачає інтерес швидше за платформу загалом; близьке до нуля — стаття просто повторює загальний тренд трафіку проєкту, а не має власного сигналу. |
| `share_of_project_pct` | Яку частку від усього трафіку свого мовного розділу займає ця тема. Потрібно для **чесного порівняння мов різного розміру** — маленька мовна спільнота завжди матиме менші абсолютні перегляди, але не обов'язково менший відносний інтерес. |
| `avg_views_per_day` | Середня кількість переглядів на день за період (після відкидання неповних періодів і викидів). Базове число для оцінки масштабу — і для перевірки, чи взагалі вистачає даних для надійного висновку. |
| `confidence` (`high`/`medium`/`low`) | Наскільки статистично надійний сам тренд (достатньо даних, стабільність, чи справді лінія тренду пояснює коливання) — **не** наскільки можна довіряти цьому як бізнес-сигналу (перегляди Wikipedia ≠ намір платити чи навчатись, це окреме застереження). |
| `r_squared` | Наскільки добре пряма лінія тренду описує реальні коливання даних (від 0 до 1). Низьке значення означає "дані надто шумні, лінійного тренду по суті немає" — це один із факторів, що впливає на `confidence`. |
| `total_periods` / `periods_used_for_trend` | Скільки періодів (місяців/днів) даних отримано всього, і скільки з них реально пішло в розрахунок тренду (після відкидання неповних періодів і викидів). Різниця між цими двома числами одразу показує, скільки даних "відфільтровано". |
| `outliers` | Список конкретних дат, які визначено як аномальні сплески/провали і виключено з розрахунку тренду (детальніше — розділ 5 вище). Ці точки й далі видно на графіку, просто не враховані в підсумковий відсоток. |

### Чому одночасно можна порівняти не більше 5 мов/тем (`make_report.py`)

Технічно `resolve_topic.py` і `fetch_pageviews.py` можуть обробити набагато більше мов (перший навіть має власний ліміт — 100, суто щоб не зависнути на явно абсурдному запиті). Але сам звіт (`make_report.py`) свідомо обмежує кількість елементів на одному графіку/в одному PDF до **5**, і це окреме, навмисне обмеження — практика показала, що більша кількість кривих одночасно робить результат гірше читабельним, а не інформативнішим:

- **Легенда графіка ламається.** Кожен підпис — це код мови плюс, часто, короткий коментар (наприклад, "pl (Głodówka lecznicza — related concept)"). При 5 підписах легенда під графіком ще влазить у два-три рядки; при 20-30 вона займає більше місця, ніж сам графік, і підписи починають накладатись/обрізатись.
- **Логарифмічна шкала (яка вмикається автоматично, якщо серії відрізняються більш ніж у 20 разів) стає менш читабельною**, коли на ній одночасно 20+ ліній різного кольору — знайти й порівняти дві конкретні криві серед такої кількості практично неможливо, навіть з клікабельною легендою в інтерактивній HTML-версії.
- **Розділ "Припущення та обмеження" в PDF росте лінійно з кількістю мов** (по блоку припущень на кожну), тож при великій кількості мов односторінковий звіт неминуче перетворюється на багатосторінковий текст, який важко проглянути.
- Ціль звіту — допомогти прийняти рішення, а не показати всі можливі дані одразу. 5 — це число, яке дає змогу побачити реальних "фіналістів" порівняння (наприклад, топ-5 за швидкістю росту чи за розміром ринку), не перетворюючи чарт на кольоровий шум.

Якщо користувач просить порівняти більше 5 мов/тем — очікується, що агент або звужує список до топ-5 за узгодженим з користувачем критерієм (див. "Вибір критерію перспективності" в `SKILL.md`) і явно каже, що і за яким критерієм відкинув, або будує кілька окремих звітів по 5 замість одного нечитабельного.

## Плани на майбутнє

- **Реальна база даних замість JSON-файлів.** Зараз кеш і архів даних — це плоскі JSON-файли на диску (`cache/`, `data/`). Це просто і не потребує додаткової інфраструктури, але погано масштабується: складно робити вибіркові запити ("покажи всі теми, які я аналізував для польської мови"), немає індексів, ризик дублювання. Природний наступний крок — SQLite (не потребує окремого сервера, просто файл) або повноцінна БД, якщо обсяг використання зросте.
- **Термін придатності (TTL) кешу.** Зараз кеш ніколи не видаляється сам — свіжість перевіряється вручну через `cache_age_days` і рішення користувача. Автоматичний TTL (наприклад, "перезапитати, якщо даним більше N днів") прибрав би цей ручний крок для рутинних запитів.
- **Розбивка по типах пристроїв/доступу.** Як згадано вище — окремі графіки desktop/mobile-web/mobile-app для конкретної теми (наразі Wikimedia API не дає такого зрізу напряму для однієї статті, лише для всього мовного розділу).
- **Сезонність-обізнане виявлення викидів** (наприклад, STL-декомпозиція) замість глобального медіана/MAD-тесту — щоб коректно відрізняти "разова аномалія" від "щорічний сезонний патерн" і від "природний початок сильного тренду".
- **Перевірити й уточнити "магічні числа" в коді.** У кількох місцях є фіксовані пороги, які визначають рішення скрипта. Наприклад: якщо в статті менше ~15 переглядів на день — висновок автоматично вважається ненадійним (`confidence: low`); або коли пошук теми знаходить кілька однаково схожих варіантів, ми обираємо один із них автоматично, лише якщо він щонайменше **втричі** популярніший за наступний за ним — інакше просимо користувача уточнити самому. Ці конкретні цифри (15 переглядів/день, поріг "у 3 рази") ми підбирали вручну під час розробки, дивлячись на десяток-другий реальних тестових запитів — вони добре спрацювали на тому, що ми перевірили, але це не суворо виведені наукові константи. Якщо навичка буде використовуватись значно ширше, варто перевірити ці пороги на набагато більшій і різноманітнішій кількості реальних запитів і за потреби скоригувати.
- **Більш інтерактивні/багатші графіки.** Зараз є і статичний PNG (matplotlib), і інтерактивний HTML (через Plotly — клік по легенді ховає/показує криву, drag для зуму по часу, ховер з точними значеннями), але сам graph — це доволі простий лінійний графік. Можна піти далі: повноцінна дашборд-бібліотека (наприклад, Dash) або ширше використання можливостей Plotly — кілька синхронізованих панелей (наприклад, окремо графік і таблиця метрик поруч), випадаючі фільтри для перемикання періоду/метрики просто в самому файлі, анотації подій прямо на графіку тощо.
- **Пошук суміжних/пов'язаних тем через граф Wikidata** — щоб пропонувати користувачу "а ось ще теми, варті дослідження" на основі семантичних зв'язків, а не лише відповідати на прямий запит.
- **Паралельне завантаження** багатьох мов одночасно (з урахуванням rate limit) — зараз запити йдуть послідовно, що при великій кількості мов (30+) стає повільним.
- **Розумніший спосіб порівнювати більше 5 мов/тем, ніж плоский ліміт.** Зараз `make_report.py` просто відмовляється будувати звіт більш ніж на 5 елементів (див. розділ вище про читабельність). Це чесне й просте рішення, але не єдино можливе — замість жорсткого ліміту можна зробити: (1) автоматичне попереднє ранжування всіх запитаних мов/тем за обраним критерієм і показ лише топ-5 у звіті, а решти — коротким текстовим списком без графіка; (2) "групові" звіти, де замість 20 окремих кривих на одному графіку показується 4-5 агрегованих груп (наприклад, по регіону); (3) для інтерактивної HTML-версії — фільтр/чекбокси, які дозволяють користувачу самому вмикати/вимикати мови з набагато більшого набору, а не бачити всі криві одночасно за замовчуванням.
- **Автоматизовані тести.** Зараз уся перевірка коректності статистики й дисамбігуації робилась вручну, на реальних прикладах під час розробки — набір автоматичних тестів захистив би від регресій при майбутніх змінах.
- **Missing-language fallback (переклад теми й пошук суміжного поняття).** Була експериментальна логіка: якщо статті немає в потрібній мові, перекласти тему й спробувати знайти **суміжне** поняття Wikidata в цій мові (це реально спрацьовувало — наприклад, "intermittent fasting" не має польської статті, але пов'язане поняття "Głodówka lecznicza" / лікувальне голодування має, і воно "невидиме" для англомовного пошуку, бо не має англійської назви). Її прибрали, бо знайдена "заміна" часто виявлялась змістовно іншою темою, а не тим самим поняттям іншою мовою — ризик тихо порівняти дві різні речі під одним ярликом. Правильна версія цієї ідеї потребує надійнішого способу підтвердити, що замінник дійсно еквівалентний (чи хоча б порівнянний) оригінальній темі, перш ніж його використовувати — наприклад, перевірка семантичних зв'язків між QID у самій Wikidata, або явне підтвердження від користувача перед тим, як включати замінник у звіт.
